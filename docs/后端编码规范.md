# 高校公寓管理系统 后端编码规范
## 1. 代码风格规范
### 1.1 命名规范
- 类名：大驼峰命名，见名知意，如 `UserController`、`DormBuildingService`；数据库实体类后缀统一为 `DO`，如 `SysUserDO`
- 方法名：小驼峰命名，动词开头，如 `addBuilding`、`queryRepairList`
- 常量：全大写 + 下划线分隔，定义在枚举或类常量区
- 包名：全小写，按业务模块分层，如 `com.dorm.controller`、`com.dorm.service`
- 接口实现类：后缀统一为 `Impl`，如 `UserServiceImpl`

### 1.2 分层与职责
- 严格遵循三层架构：Controller 层负责请求接入、参数校验、结果封装；Service 层负责业务逻辑、事务控制；Mapper 层负责数据访问
- 禁止跨层调用，禁止 Controller 层直接操作数据库
- 单一职责原则，单个方法长度不超过 80 行，复杂逻辑拆分为子方法
- 实体类分层：DO 对应数据库表，VO 对应前端返回，DTO 对应业务传输，禁止混用

### 1.3 代码健壮性
- 所有公共方法入参必须做空值校验，核心参数强制非空判断
- 集合遍历、数组访问必须做边界检查，避免索引越界
- 类型转换必须校验合法性，避免类型转换异常

### 1.4 注释规范
- 类、公共接口方法必须添加 Javadoc 注释，说明功能、入参、返回值、可能抛出的异常
- 核心业务逻辑、复杂计算必须添加行内注释，说明设计意图
- 枚举值、常量必须注释说明业务含义

## 2. 异常处理规范
### 2.1 异常分类
- 业务异常：`BusinessException`，用于业务规则校验失败（如床位已占用、账号不存在），携带错误码与用户可读提示信息
- 系统异常：`SystemException`，用于底层基础设施故障（如数据库连接失败）
- 参数校验异常：由 Validation 框架抛出，统一拦截处理

### 2.2 处理原则
- **本地优先**：当前层可处理的异常必须就地处理（重试、返回默认值、转化为业务异常），严禁向上抛出未处理的原生异常
- **具体捕获**：禁止空 catch、禁止泛化 `catch(Exception)` 吞异常；必须捕获具体异常类型，仅全局异常处理器可捕获 `Exception`
- **数据一致性**：数据库写入、状态变更等不可逆操作必须包裹事务，异常触发自动回滚，禁止产生脏数据
- **安全输出**：禁止向前端返回异常堆栈，所有异常统一转化为标准错误码与业务提示

### 2.3 强制约束
1. 禁止使用 `try { ... } catch (Exception e) { }` 静默吞掉异常
2. 禁止直接将原生 RuntimeException 抛出到 Controller 层，必须包装为业务异常或由全局异常处理器统一处理
3. 外部依赖调用必须设置超时时间，失败时提供降级逻辑
4. 业务异常必须在方法注释中说明触发场景与对应错误码

## 3. 日志规范
### 3.1 日志框架与分级
- 统一使用 SLF4J + Logback，禁止使用 `System.out` 打印输出
- 日志分级规则：
  - DEBUG：开发调试细节，生产环境默认关闭
  - INFO：关键业务事件（登录、入住办理、报修状态流转），记录操作人、核心参数与操作结果
  - WARN：非预期但可恢复的场景，如参数格式不合法、重试执行
  - ERROR：系统故障、业务失败，必须记录完整异常堆栈

### 3.2 强制约束
1. 异常日志必须使用 `log.error("业务描述: {}", 参数, e)` 输出完整堆栈，禁止只打印异常消息
2. 禁止日志中输出密码、身份证号等敏感信息
3. 核心业务操作必须记录 INFO 日志，包含操作主体与操作结果
4. 禁止在循环中打印大量冗余日志
5. 操作日志由 Spring AOP 统一切面记录，禁止在业务代码中散落日志逻辑

## 4. 硬编码与常量治理
### 4.1 分类处理规则
| 类型 | 示例 | 实现方式 |
| :--- | :--- | :--- |
| 业务状态/类型 | 入住状态、报修状态、用户角色 | 模块内定义 Enum 枚举类，禁止使用数字/字符串字面量 |
| 业务固定常量 | 默认分页大小、密码加密盐值 | 模块内类级常量（`static final`），就近定义 |
| 技术配置项 | 连接超时、令牌过期时间 | `application.yml` 配置，通过 `@ConfigurationProperties` 注入，代码提供默认值 |
| 环境依赖项 | 数据库地址、账号密码 | 配置文件/环境变量注入，代码中禁止出现明文值 |

### 4.2 强制约束
1. 业务状态、类型必须使用 Enum 表示，禁止在业务逻辑中直接写 `0/1`、`"student"/"admin"` 等字面量
2. 禁止创建跨多业务域的全局常量类，常量随所属模块定义
3. 配置项必须有代码默认值，配置文件注释必须包含含义、单位、默认值
4. 禁止在生产代码中出现调试用临时硬编码（如固定测试账号、休眠等待）

## 5. 数据访问规范
1. 所有 SQL 通过 MyBatis-Plus 预编译实现，禁止字符串拼接 SQL，杜绝 SQL 注入风险
2. 分页查询统一使用 MyBatis-Plus 分页插件，禁止手动计算分页参数
3. 批量数据操作使用批量插入/更新方法，禁止循环单条执行
4. 核心写操作（入住分配、报修状态变更）必须添加 `@Transactional` 事务注解
5. 关联查询优先在业务层组装，避免编写过度复杂的多表联查 SQL

## 6. 接口与权限规范
1. 所有接口入参使用 `@Validated` 做参数校验，必填、长度、格式校验前置
2. 所有接口返回统一 `Result` 封装类，包含 `code`、`msg`、`data` 字段
3. 接口级权限校验由拦截器统一实现，禁止在业务代码中散落权限判断逻辑
4. 越权访问、未登录访问统一返回标准错误码，不泄露系统内部细节

## 7. 代码审查验收标准
出现以下任意一项视为代码不合格：
1. 存在空 catch、静默吞异常的代码
2. 业务逻辑中出现未定义为枚举/常量的魔法值（数字、字符串字面量重复出现）
3. 直接向前端返回异常堆栈信息
4. 存在 SQL 拼接注入风险
5. 核心写操作未添加事务控制
6. 使用 `System.out` 打印日志或敏感信息明文输出
7. 跨层调用、职责混乱的代码结构
