# 高校公寓管理系统 后端架构设计文档

适配：Spring Boot 2.7.x + MyBatis-Plus + Sa-Token / 4-5人协作 / 7天开发周期

## 一、架构概述

### 1.1 设计目标

1. **分层解耦**：采用标准三层架构，各层职责边界清晰，支撑多人并行开发，降低协作冲突
2. **规范统一**：公共组件下沉复用，统一返回、异常、日志、权限等基础能力，业务开发仅需关注核心逻辑
3. **可维护性**：代码结构标准化，命名与分层约定明确，符合Java工程开发规范，降低后续维护成本
4. **练手适配**：覆盖SSM核心能力升级场景，保留事务、AOP、权限拦截等核心技术点，兼顾开发效率与学习目标

### 1.2 技术栈总览

| 分层     | 技术组件          | 版本   | 核心作用                            |
| -------- | ----------------- | ------ | ----------------------------------- |
| Web层    | Spring Boot Web   | 2.7.18 | RESTful接口能力、内置Tomcat容器     |
| 权限层   | Sa-Token          | 1.37.x | 登录态校验、角色权限拦截、Token管理 |
| 持久层   | MyBatis-Plus      | 3.5.5  | 通用CRUD、分页、条件构造、自动填充  |

## 二、整体分层架构

### 2.1 架构分层模型

采用经典四层架构，从上至下依赖单向传递，禁止反向依赖与跨层调用：

```
┌─────────────────────────────────┐
│ Controller 控制层               │  请求接入、参数校验、结果封装
├─────────────────────────────────┤
│ Service 业务层                  │  业务逻辑、事务控制、规则校验
├─────────────────────────────────┤
│ Mapper 数据访问层               │  数据库读写、SQL封装
├─────────────────────────────────┤
│ MySQL 数据库                    │  数据持久化存储
└─────────────────────────────────┘
       ↑ 公共组件横切所有分层
┌─────────────────────────────────┐
│ 公共组件层（Common）            │  统一返回、异常、工具、常量、配置
└─────────────────────────────────┘
```

### 2.2 层间依赖规则

1. Controller 仅依赖 Service，不直接调用 Mapper 或操作数据库
2. Service 仅依赖 Mapper 与公共组件，不引入 Web 层对象（如 HttpServletRequest）
3. Mapper 层仅做数据访问，不包含任何业务逻辑
4. 公共组件层被所有层依赖，不得依赖业务层代码

## 三、分层详细设计

### 3.1 控制层（Controller）

#### 职责

- 接收前端HTTP请求，完成参数接收与基础校验
- 调用Service层执行业务逻辑
- 封装统一返回结果，响应前端
- 接口级权限标注，配合拦截器完成权限校验

#### 开发规范

- 类名以 `Controller` 结尾，按业务模块划分
- 方法遵循RESTful风格：新增POST、修改PUT、删除DELETE、查询GET
- 所有接口方法返回值统一为 `Result<T>`
- 入参使用 `@Validated` 开启参数校验
- 不编写业务判断逻辑，仅做参数透传与结果封装

### 3.2 业务层（Service）

#### 职责

- 核心业务逻辑实现、业务规则校验
- 事务控制，保障数据一致性
- 多表数据组装与业务流转
- 业务异常抛出与业务状态判断

#### 开发规范

- 采用接口+实现类模式：接口定义在 `service` 包，实现类放在 `service.impl` 包，后缀 `Impl`
- 核心写操作、多表变更方法必须添加 `@Transactional` 事务注解
- 业务规则校验失败统一抛出 `BusinessException`，携带错误码与提示信息
- 单方法职责单一，复杂逻辑拆分为私有子方法

### 3.3 数据访问层（Mapper）

#### 职责

- 单表CRUD：基于MyBatis-Plus BaseMapper实现
- 复杂查询：自定义XML或注解SQL，实现多表关联、条件查询
- 批量操作：批量插入、批量更新数据访问

#### 开发规范

- 接口名以 `Mapper` 结尾，继承 `BaseMapper<DO>`
- 简单查询使用条件构造器，复杂多表查询编写XML SQL
- 所有SQL采用预编译方式，禁止字符串拼接
- 禁止在Mapper中编写业务逻辑

### 3.4 实体对象分层规范

所有实体按职责拆分，禁止跨场景混用：

| 实体类型     | 后缀  | 存放位置     | 作用                                                         |
| ------------ | ----- | ------------ | ------------------------------------------------------------ |
| 数据对象     | DO    | entity.po    | 与数据库表一一对应，仅用于数据传输；默认直接作为接口返回对象（注：`do` 为 Java 关键字，包名不可用，采用 `po`） |
| 视图对象     | VO    | entity.vo    | 返回前端的展示对象，仅在 DO 无法满足展示字段（如冗余联查字段）时按需创建 |
| 数据传输对象 | DTO   | entity.dto   | 前后端提交参数传输，仅在入参聚合多个实体字段时创建，简单入参直接使用 DO 或基础类型 |
| 查询对象     | Query | entity.query | 分页条件查询入参封装，所有分页查询必须使用                   |

**简化原则**：默认使用「DO + Query」组合完成接口开发，禁止为每个接口机械创建 VO/DTO 三件套；仅当返回字段需要联查冗余（如楼栋名称、操作人姓名）或入参结构复杂时才创建 VO/DTO。

## 四、核心公共组件设计

### 4.1 统一返回结果封装

- 全局统一响应类 

  ```
  Result<T>
  ```

  ，包含三个核心字段：

  - `code`：状态码，200成功，其他为错误码
  - `msg`：提示信息
  - `data`：响应数据

- 提供静态工具方法：`success()`、`success(data)`、`fail(code, msg)`

- 所有Controller接口必须返回该类型，由全局异常处理器兜底异常场景

### 4.2 全局异常处理

- 基于 `@RestControllerAdvice` 实现全局异常拦截，统一封装为 `Result` 返回
- 异常分类处理规则：
  1. **业务异常 BusinessException**：捕获并返回业务错误码与提示信息，不打印错误堆栈
  2. **参数校验异常**：捕获校验注解抛出的异常，拼接字段错误提示返回
  3. **权限异常**：捕获未登录、越权异常，将 HTTP 状态码置为 401（未登录）/403（无权限），body 仍返回统一 Result 结构
  4. **系统异常 Exception**：捕获所有未处理异常，返回通用系统错误提示，打印完整错误堆栈
- 禁止向前端返回异常堆栈与原生错误信息

### 4.3 操作日志切面

- 基于Spring AOP实现，自定义 `@OperationLog` 注解，仅标注在管理员角色写操作（增删改）接口上，学生查询类操作不记录
- 注解属性：`module`（模块）、`type`（操作类型）、`desc`（操作描述）
- 切面自动获取：操作人ID、操作人姓名、请求IP、请求参数、操作时间、执行结果
- 日志持久化至 `sys_operation_log` 表，支持审计追溯
- 业务代码中无需手动编写日志记录逻辑

### 4.4 权限认证体系

- 基于Sa-Token实现Token模式的登录认证与角色权限控制
- 核心机制：
  1. 登录成功后生成Token返回前端，前端将Token放入请求头（默认请求头名 `satoken`）请求接口；Token 有效期 1 天，过期后需重新登录，不实现自动续期
  2. 全局拦截器校验登录态，未登录请求直接返回401
  3. 接口级角色校验：通过注解 `@SaCheckRole("admin")` 限制角色访问权限
  4. 数据权限：学生角色仅可查询本人数据，由Service层通过当前登录用户ID过滤
- 提供 `LoginUserUtil` 工具类，全局获取当前登录用户ID、角色、姓名

### 4.5 分页组件

- 基于MyBatis-Plus分页插件实现统一分页能力
- 分页查询入参统一继承 `PageQuery`，包含 `pageNum`、`pageSize` 字段
- 分页返回统一使用 `PageVO`，包含总条数、总页数、当前页数据列表
- 所有列表查询接口必须支持分页，禁止全量查询

### 4.6 事务管理机制

- 采用声明式事务 `@Transactional`，标注在Service层写操作方法上
- 事务回滚规则：默认回滚RuntimeException，业务异常继承RuntimeException自动触发回滚
- 多表写操作、状态流转操作必须添加事务，保障数据一致性
- 禁止在Controller层添加事务注解

## 五、核心业务模块架构设计

### 5.1 用户认证与权限模块

- **类结构**：`UserController` / `UserService` / `UserMapper` / `SysUserDO`

- 核心流程

  1. 登录：校验账号密码 → 生成Token → 返回用户信息与角色
  2. 权限校验：拦截器全局校验登录态 → 接口注解校验角色
  3. 个人信息修改：校验原密码 → 更新用户信息
  
- **核心规则**：密码BCrypt加密存储，禁止明文比对与返回；登录失败仅返回统一错误提示，不实施连续失败锁定策略
- **用户管理**：管理员维护学生账号，支持创建（初始密码统一为 123456）、编辑、重置密码、禁用/启用，创建与编辑时校验学号唯一

### 5.2 宿舍基础信息模块

- **类结构**：按领域拆分三个独立模块，分别对应楼栋、房间、床位

- 核心约束

  1. 三级数据关联，删除时校验下级是否存在数据，存在则禁止删除
  2. 房间、床位编号联合楼栋/房间唯一，重复数据拦截
  3. 支持批量初始化床位，批量操作包裹事务

### 5.3 入住管理模块

- **类结构**：`CheckinController` / `CheckinService` / `CheckinMapper`

- 核心事务流程（入住分配）

  1. 使用 `SELECT ... FOR UPDATE` 锁定目标床位行，校验状态是否为空闲（防止并发重复分配）
  2. 校验学生是否已有有效入住记录
  3. 更新床位状态为「已入住」
  4. 插入入住记录，状态为「入住中」
  5. 以上操作同一事务，失败全部回滚
  
- **退宿流程**：更新入住记录状态与退宿时间 → 释放床位状态，事务保障

### 5.4 报修管理模块

- **类结构**：`RepairController` / `RepairService` / `RepairMapper`

- 状态流转规则

  - 初始状态：待处理
  - 可流转：待处理 → 处理中 → 已完成，禁止跳转与逆向流转
  - 终态：已完成，不可再次修改

- **核心约束**：状态变更校验合法性，非法流转抛出业务异常；标记「已完成」时必须填写处理结果，回填处理人与处理时间；学生无有效入住记录时禁止提交报修；列表查询返回 `isOverdue` 字段（待处理且提交超过 24 小时为 true），供前端超时高亮渲染

## 六、安全架构设计

### 6.1 认证安全

- Token 有效期 1 天，过期后需重新登录，不实现自动续期与连续失败锁定
- 密码采用BCrypt强哈希加密存储，不可逆
- 登录失败返回统一错误提示，不泄露账号是否存在的信息
- 越权访问统一拦截，不泄露数据存在性信息

### 6.2 数据安全

- 所有SQL通过MyBatis-Plus预编译执行，杜绝SQL注入
- 敏感字段（密码）不在日志、接口返回中明文展示
- 删除采用物理删除，删除前必须校验下级关联数据存在性，存在关联数据时禁止删除

### 6.3 输入安全

- 所有接口入参开启参数校验，限制长度、格式、范围
- 特殊字符过滤，防范XSS风险
- 非法参数直接拦截，不进入业务逻辑

## 八、数据库访问规范

1. 主键策略：使用数据库自增主键，类型为 `bigint`
2. 公共字段自动填充：`create_time`、`update_time` 由MyBatis-Plus自动填充，业务代码无需手动赋值
3. 查询优化：核心查询字段建立索引，列表查询必须分页，禁止大表全量查询
4. 批量操作：超过5条数据的写入/更新必须使用批量方法，禁止循环单条执行
5. 关联查询：单表查询优先使用条件构造器，多表关联查询优先在XML中编写

## 九、非功能设计保障

### 9.1 性能保障

- 单接口响应时间≤1s，核心查询字段建索引
- 列表接口强制分页，默认每页10条
- 避免循环内查询数据库，采用批量查询+内存组装方式

### 9.2 可维护性保障

- 分层清晰，职责单一，模块间低耦合
- 统一异常、统一返回、统一日志，问题排查路径明确
- 核心方法与复杂逻辑必须添加注释

### 9.3 可扩展性保障

- 业务模块独立拆分，新增模块不影响现有代码
- 公共组件可复用，新增业务无需重复开发基础能力
- 状态、类型均使用枚举，新增状态无需修改大量硬编码

## 十、开发协作边界说明

1. **公共组件优先开发**：Day1完成统一返回、全局异常、分页、权限拦截、数据库配置等基础组件，作为所有业务开发的底座
2. **业务模块并行开发**：各业务模块独立，按模块分配开发人员，Controller/Service/Mapper垂直拆分，减少代码冲突
3. **接口契约先行**：开发前确定接口入参、出参字段，同步更新Knife4j文档，前后端基于契约并行开发
4. **提交粒度**：按功能点提交代码，单次提交对应单一功能，便于代码评审与问题回溯
