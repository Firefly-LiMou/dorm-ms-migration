# 高校公寓管理系统（协作练手版）需求分析文档 V1.0

适配：大二计算机专业 / 4-5 人团队 / 7 天开发周期 / Spring Boot + Vue3 全栈练手 核心目标：掌握 Git+GitHub 团队协作、前后端分离开发流程、小团队敏捷分工

## 一、项目概述

### 1.1 项目背景与建设目标

本项目为团队协作开发练手项目，以高校学生公寓日常管理为业务载体，基于 Spring Boot + Vue3 前后端分离架构，在一周周期内完成可运行、可部署的完整 Web 应用。 项目以「协作流程规范」为核心导向，通过小项目完整落地多人 Git 协作、前后端并行开发、接口联调全流程，为后续中大型项目协作奠基，同步达成以下目标：

1. 熟练掌握 Git 分支管理、代码提交、PR 评审、冲突解决等团队协作技能
2. 落地 Spring Boot + Vue3 全栈技术栈，理解前后端分离架构的开发模式
3. 建立工程规范意识，形成统一的代码风格、接口规范与文档习惯
4. 实践小团队敏捷分工与进度管控，提升协作效率

## 二、用户角色与权限划分

系统设置两类用户角色，采用基于角色的权限控制，后端接口级校验，前端菜单动态展示，越权访问统一拦截。

| 角色       | 权限范围                                                     | 核心定位                       |
| ---------- | ------------------------------------------------------------ | ------------------------------ |
| 学生       | 仅可操作与本人相关的功能，查看个人住宿信息、提交报修、查看本人报修记录 | 业务发起方，系统服务对象       |
| 系统管理员 | 全系统功能权限，可管理楼栋 / 房间 / 床位、学生入住分配、报修处理、操作日志查看 | 全局管控方，业务执行与数据维护 |

## 三、功能需求说明

功能按交付优先级分为「必做核心模块」与「可选扩展模块」；必做模块为 7 天周期必须落地的内容，保障核心链路闭环与协作练手目标；可选模块为进度提前时的加分项，弹性落地。

### 3.1 必做核心模块（7 天周期保障交付）

#### 3.1.1 用户认证与权限管理模块

**对应练手点**：拦截器、AOP 切面、统一返回封装、前后端权限联动

- 登录 / 登出：支持两类角色通过账号密码登录，Token 登录态管理，安全退出
- 权限拦截：后端接口级角色权限校验，未登录 / 越权访问返回统一错误码；前端基于角色动态展示菜单，路由守卫拦截未登录访问
- 个人信息维护：所有角色可查看、修改个人基础信息与登录密码
- 用户管理：管理员可创建、编辑学生账号，重置学生登录密码（重置后恢复为初始密码 123456），禁用 / 启用学生账号
- 操作日志：管理员所有增删改操作，通过 Spring AOP 自动记录操作人、操作时间、操作内容、请求 IP，支持列表查询与追溯

#### 3.1.2 宿舍基础信息与入住管理模块

**对应练手点**：多表关联查询、分页查询、事务管理、参数校验

- 楼栋管理：管理员可新增、编辑、删除楼栋信息（楼栋号、楼栋名称、楼层数、所属区域）
- 房间管理：管理员按楼栋维护房间信息（房间号、所属楼栋、楼层、床位数、房间类型），支持按楼栋、房间号筛选查询
- 床位管理：管理员维护床位信息（床位号、所属房间、入住状态），支持批量初始化房间床位
- 入住分配：管理员从已创建的学生账号中选择学生，为其分配空闲床位、办理退宿，自动更新床位状态，生成入住记录
- 数据关联：楼栋 - 房间 - 床位 - 学生四级关联，删除采用物理删除，删除前必须校验下级数据存在性，存在下级数据时禁止删除；核心操作添加事务保障数据一致性
- 信息查询：学生可查看本人当前住宿信息；管理员可全局查询所有学生住宿信息，支持按楼栋、学号筛选

#### 3.1.3 报修管理模块

**对应练手点**：状态流转、条件查询、分页、前后端联调

- 报修提交：学生填写报修单（报修类型、报修内容、联系电话），提交后状态为「待处理」，自动关联学生所在房间；无有效入住记录的学生禁止提交报修
- 报修处理：管理员查看全部报修单，按「待处理 → 处理中 → 已完成」顺序流转，禁止跳转与逆向流转；标记「已完成」时必须填写处理结果
- 报修查询：学生可查看本人报修记录与处理进度；管理员可按状态、时间、楼栋筛选查询
- 超时标识：列表中对提交超过 24 小时仍处于「待处理」状态的报修单做高亮标识，超时标识由后端计算 isOverdue 字段返回，前端仅负责渲染

### 3.2 可选扩展模块（进度充裕时落地）

#### 3.2.1 调宿申请审批

- 学生提交调宿申请，选择目标空闲床位、填写申请原因
- 管理员审核申请，审批通过后自动调整床位状态、生成调宿记录；驳回需填写原因

#### 3.2.2 晚归登记管理

- 管理员录入晚归学生信息，自动关联学生住宿信息
- 按楼栋、日期筛选查询晚归记录，支持月度简单统计

#### 3.2.3 公告通知模块

- 管理员发布公寓公告，支持置顶、下架
- 学生、管理员登录后可查看公告列表与详情

#### 3.2.4 系统增强特性

- 登录图形验证码
- 敏感操作二次确认
- 数据批量导入导出（Excel）

## 四、核心业务流程

### 4.1 学生入住分配流程

1. 管理员提前维护楼栋、房间、床位基础数据，确保存在空闲床位
2. 管理员在用户管理中创建学生账号（初始密码 123456），从空闲床位中选择完成分配
3. 系统校验床位状态，事务性更新床位状态为「已入住」，并生成入住记录
4. 学生账号登录后可查看个人住宿信息

### 4.2 报修处理全流程

1. 学生登录系统，填写报修单并提交，状态为「待处理」
2. 管理员登录系统，查看待处理报修单列表
3. 管理员处理报修后，更新状态为「已完成」，填写处理结果
4. 学生可查看报修处理进度与结果

## 五、非功能需求

### 5.1 性能需求

- 单接口响应时间 ≤ 1s，列表查询默认分页，每页 10 条
- 数据库核心查询字段（学号、楼栋号、状态）建立索引，避免全表扫描
- 支持 50 人同时在线使用，无明显卡顿与数据错误

### 5.2 安全需求

- 所有 SQL 通过 MyBatis-Plus 预编译实现，杜绝 SQL 注入风险
- 后端接口统一做权限校验，禁止越权访问他人数据与其他角色功能
- 密码使用 BCrypt 加密存储，禁止明文保存与明文比对
- 登录 Token 有效期 1 天，过期后需重新登录，不实施自动续期与连续失败锁定；登录失败仅返回统一错误提示
- 输入参数做合法性校验，过滤特殊字符，避免 XSS 风险

### 5.3 工程与可维护性需求

- 采用标准三层架构（Controller/Service/Mapper），分层清晰，职责明确
- 统一返回格式、统一全局异常处理、统一错误码，便于前后端联调与问题排查
- 核心业务方法添加事务注解，保证数据一致性
- 代码遵循阿里巴巴 Java 开发规范，命名规范、关键逻辑注释完整
- 前端组件化开发，页面与逻辑拆分合理，避免冗余代码

### 5.4 团队协作规范（强制要求）

#### （1）Git 协作规范

- 分支模型与开发流程：采用轻量主干集成工作流，`main`（最终交付）/ `dev`（开发集成主干）双长期分支 + `feature/*`、`bugfix/*` 临时分支，Squash Merge 合并，每日集成；完整流程以 `docs/开发工作流.md` 为准

- 提交规范：采用 Conventional Commits 规范，格式为

  ```
  type: 描述
  ```

  ，例如：

  - `feat: 新增报修提交接口`
  - `fix: 修复床位状态更新异常问题`
  - `docs: 更新需求文档`
  - `style: 格式化代码`

- 代码评审：所有 PR 需至少 1 名队友评审通过后方可合并，禁止直接向 main/dev 分支提交代码（由 GitHub 分支保护规则平台强制）

#### （2）接口规范

- 采用 RESTful 风格接口，统一请求路径、请求方法命名规范
- 所有接口返回统一 JSON 格式，包含状态码、提示信息、返回数据
- 接口开发前先约定字段名、参数类型、响应结构，后端同步更新 Knife4j 文档，前端基于文档并行开发

#### （3）环境统一

- 全团队统一 JDK 1.8、MySQL 8.0、Node.js 22 LTS 版本（Vite 5 要求 Node 18+，22/24 均满足，统一采用 22 LTS）
- 提供统一的数据库初始化 SQL 脚本，项目启动即可导入基础数据
- 配置文件统一模板，敏感配置（数据库密码等）本地自行配置，不提交至 Git 仓库

## 六、交付与验收标准

### 6.1 交付物清单

1. 完整可运行的后端项目代码、前端项目代码
2. 数据库初始化 SQL 脚本 + 部署说明文档
3. GitHub 仓库完整提交记录、分支历史、PR 评审记录
4. 需求文档、接口说明文档

### 6.2 验收标准

1. **协作合规性（优先级最高）**：Git 分支规范、提交格式符合要求，有完整的 PR 评审记录，多人协作痕迹清晰
2. **功能完整性**：必做 3 大模块 100% 落地，核心业务流程可完整跑通，无阻断性 Bug
3. **工程规范性**：前后端分层清晰，代码命名规范，统一返回、全局异常、AOP 日志等基础特性完整落地
4. **可运行性**：提供初始化脚本，可在本地一键启动前后端项目，正常访问使用
5. **文档完整性**：交付文档齐全，说明清晰，可支撑项目部署与功能验证
