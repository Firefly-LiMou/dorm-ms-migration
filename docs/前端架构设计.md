# 高校公寓管理系统 前端架构设计文档

## 一、架构概述

### 1.1 设计目标

1. **分层解耦**：采用标准前端分层架构，各层职责边界清晰，支撑多人并行开发，降低Git协作冲突
2. **规范统一**：公共能力下沉复用，统一请求、权限、状态、组件、异常处理，业务开发仅聚焦页面与交互逻辑
3. **体验一致**：基于Element Plus封装通用业务组件，统一交互模式、提示规则、页面布局，保障全项目交互体验统一
4. **练手适配**：覆盖前后端分离核心开发模式，落实路由守卫、状态管理、接口封装、组件化开发等核心前端能力

### 1.2 技术栈总览

| 分层       | 技术组件                    | 版本   | 核心作用                                  |
| ---------- | --------------------------- | ------ | ----------------------------------------- |
| 核心框架   | Vue                         | 3.3.x  | 响应式视图渲染、组合式API开发             |
| 构建工具   | Vite                        | 5.x    | 项目构建、热更新、生产打包                |
| UI组件库   | Element Plus                | 2.7.x  | 基础UI组件、表单、表格、弹窗等通用能力    |
| 路由管理   | Vue Router                  | 4.x    | 页面路由、路由守卫、权限拦截              |
| 状态管理   | Pinia                       | 2.x    | 全局状态管理，配合持久化插件存储登录态    |
| 请求工具   | Axios                       | 1.7.x  | HTTP请求封装、拦截器、统一错误处理        |
| 状态持久化 | pinia-plugin-persistedstate | 3.x    | Pinia状态本地持久化，自动同步localStorage |
| 代码规范   | ESLint + Prettier           | 稳定版 | 统一代码风格、语法检查                    |

## 二、整体分层架构

### 2.1 分层模型

采用五层单向依赖架构，依赖自上而下传递，禁止反向依赖与跨层调用：

```
┌─────────────────────────────────┐
│ 视图层 views                    │  页面组装、业务逻辑聚合、路由入口
├─────────────────────────────────┤
│ 组件层 components               │  公共组件、业务组件复用
├─────────────────────────────────┤
│ 状态层 store                    │  全局状态管理、登录态存储
├─────────────────────────────────┤
│ 接口层 api                      │  接口请求封装、按模块聚合
├─────────────────────────────────┤
│ 工具层 utils                    │  通用工具、常量、配置、请求基础封装
└─────────────────────────────────┘
```

### 2.2 层间依赖规则

1. 视图层可依赖组件层、状态层、接口层、工具层，负责页面逻辑编排
2. 组件层仅可依赖工具层、状态层，禁止直接调用接口层API
3. 状态层仅可依赖接口层与工具层，负责数据持久化与全局状态同步
4. 接口层仅可依赖工具层的请求封装，禁止引入视图、组件相关逻辑
5. 工具层为最底层，被所有层依赖，不得依赖业务代码

## 三、分层详细设计

### 3.1 视图层（views）

#### 职责

- 页面级容器，负责路由对应的完整页面渲染
- 聚合子组件、调用接口、处理业务交互逻辑
- 管理页面级状态，处理页面生命周期

#### 开发规范

- 按业务模块划分目录，单页面对应单文件
- 单个页面代码不超过500行，复杂页面拆分为多个子组件
- 必须完整覆盖加载中、空数据、错误、正常数据四种状态
- 页面级数据查询统一在`onMounted`生命周期触发，禁止在顶层作用域直接发起请求

### 3.2 组件层（components）

#### 职责

- 公共基础组件：二次封装Element Plus，统一交互与样式
- 业务组件：可复用的业务单元，如报修卡片、床位选择器

#### 开发规范

- 通用组件放在`components/common`，业务组件随对应模块目录存放
- 组件必须显式定义props类型、默认值，必填项标注required
- 组件内部维护私有状态，外部通过props/emit通信，禁止直接修改父组件数据
- 可复用组件必须覆盖空状态、禁用状态、加载状态

### 3.3 状态层（store）

#### 职责

- 存储全局共享数据：用户登录信息、Token、角色、全局配置
- 管理跨页面共享的业务状态，避免多层组件透传

#### 开发规范

- 按领域拆分模块，如`user.js`、`app.js`，禁止单文件堆积所有状态
- 状态修改必须通过actions方法，禁止直接修改state
- 用户登录态、Token必须开启持久化，刷新页面不丢失
- 页面级私有状态不得存入全局store，由组件自行维护

### 3.4 接口层（api）

#### 职责

- 按业务模块封装所有后端接口，统一管理请求地址、参数、响应
- 隔离后端接口变更，视图层仅调用api方法，不感知请求细节

#### 开发规范

- 按业务模块拆分文件，如`user.js`、`building.js`、`repair.js`
- 所有接口方法返回Promise对象，统一由请求拦截器处理基础错误
- 接口入参必须做基础合法性校验，非法参数不发起网络请求
- 禁止在视图、组件内直接使用axios/fetch发起请求

### 3.5 工具与常量层（utils）

#### 职责

- 通用工具函数：日期格式化、字符串处理、校验规则
- 基础请求封装：axios实例、拦截器、错误处理
- 业务常量、枚举值：状态、角色、配置项

#### 开发规范

- 工具函数保持纯函数特性，无副作用、可复用
- 业务常量就近定义，跨模块通用常量放在`utils/constants.js`
- 禁止在工具函数中引入视图、组件相关依赖

### 3.6 数据对象分层规范

| 类型     | 说明               | 使用场景                                  |
| -------- | ------------------ | ----------------------------------------- |
| 请求参数 | 接口入参对象       | 提交表单、查询条件，字段与后端DTO严格对齐 |
| 响应数据 | 接口返回业务数据   | 接收后端VO数据，仅在页面/组件内展示使用   |
| 页面状态 | 组件内部响应式数据 | 控制页面交互、临时状态，不与后端直接对应  |

## 四、核心公共模块设计

### 4.1 统一请求封装

基于axios封装全局请求实例，作为所有接口调用的唯一入口：

1. **请求拦截器**：统一从Pinia获取Token并添加到请求头；统一设置请求超时时间；统一添加请求标识

2. 响应拦截器

   ：统一解析后端

   ```
   Result
   ```

   结构，成功直接返回data字段；全局错误码统一处理：

   - 401：Token失效，清空登录态，跳转登录页
   - 403：无权限，提示用户并返回首页
   - 业务错误码：统一弹出错误提示
   - 网络错误/超时：弹出网络异常提示

3. **强制约束**：所有接口必须使用封装后的请求实例，禁止新建独立axios实例；禁止在业务代码中重复处理通用错误码

### 4.2 路由与权限体系

#### 路由配置规则

- 采用路由懒加载，按需加载页面组件，提升首屏速度
- 路由分为公开路由（登录页、404页）与受保护路由，受保护路由需登录后访问
- 路由元信息`meta`中配置`roles`字段，标注可访问的角色

#### 全局路由守卫

1. 白名单校验：公开路由直接放行
2. 登录态校验：无Token强制跳转登录页
3. 角色权限校验：用户角色不在路由允许范围内，跳转403页面
4. 路由跳转统一处理加载状态与页面标题

#### 菜单权限

- 侧边栏菜单基于路由配置动态生成，根据用户角色过滤无权限菜单
- 禁止前端硬编码完整菜单，必须与路由、角色绑定

### 4.3 全局状态管理

基于Pinia实现，核心模块：

1. **user模块**：存储用户ID、用户名、真实姓名、角色、Token；提供登录、登出、获取用户信息方法；开启持久化
2. **app模块**：存储全局UI配置，如侧边栏折叠状态、主题配置

#### 强制约束

- Token仅存储在Pinia与localStorage，禁止写入cookie、页面全局变量
- 用户信息必须通过接口获取，禁止前端硬编码用户权限数据

### 4.4 通用业务组件封装

基于Element Plus二次封装，统一全项目交互样式，减少重复代码：

1. **通用分页表格**：封装表格+分页器，统一分页参数、尺寸、空状态，列表页直接复用
2. **通用表单弹窗**：封装新增/编辑弹窗，统一确认、取消、校验、加载逻辑
3. **状态标签组件**：统一状态显示样式，根据枚举值自动渲染对应颜色标签
4. **查询条件栏**：统一筛选表单布局，支持折叠、重置、查询

### 4.5 常量与枚举治理

#### 分类处理规则

| 类型         | 示例                                    | 实现方式                                                 |
| ------------ | --------------------------------------- | -------------------------------------------------------- |
| 业务状态枚举 | 报修状态、入住状态、用户角色            | 定义为常量对象，key为英文标识，value包含值、标签、样式类 |
| 固定配置常量 | 默认分页大小、表单最大长度、Token有效期 | 模块级常量，通用项存放至全局constants                    |
| 环境配置     | 接口基础地址、静态资源路径              | 环境变量`.env`文件管理，通过`import.meta.env`读取        |

#### 强制约束

- 所有业务状态、角色、类型必须定义为常量，禁止在业务代码中出现数字/字符串魔法值
- 常量命名全大写下划线分隔，与后端枚举值严格一一对应
- 同一字面量出现2次及以上必须抽取为常量

## 五、核心业务模块架构设计

### 5.1 用户认证与个人中心模块

#### 页面组成

- 登录页：账号密码登录、角色默认适配、表单校验
- 个人中心：个人信息查看、密码修改

#### 核心流程

1. 登录：表单校验 → 调用登录接口 → 存储Token与用户信息 → 跳转首页
2. 鉴权：路由守卫校验登录态与角色 → 动态渲染菜单
3. 登出：清空本地状态与缓存 → 跳转登录页

### 5.2 宿舍基础信息与入住管理模块

#### 管理员端页面

- 楼栋管理：列表、新增、编辑、删除
- 房间管理：按楼栋筛选、列表、新增、编辑、删除
- 床位管理：按房间展示、批量初始化、状态管理
- 入住管理：学生入住分配、退宿办理、入住记录查询、学生住宿信息全局查询（按楼栋、学号筛选）
- 用户管理：学生账号列表、新增、编辑、重置密码（重置后为初始密码 123456）、禁用 / 启用
- 操作日志：操作日志列表查询（按操作人、模块、操作类型、时间筛选）

#### 学生端页面

- 我的住宿：查看本人当前住宿信息、历史入住记录

#### 核心交互

- 三级数据级联选择：楼栋→房间→床位
- 删除操作二次确认，有关联数据时禁止删除
- 入住分配时仅展示空闲床位，状态变更后实时刷新列表

### 5.3 报修管理模块

#### 学生端页面

- 我的报修：报修列表、状态筛选、查看详情
- 提交报修：报修表单、类型选择、内容填写

#### 管理员端页面

- 报修管理：全量报修列表、多条件筛选、状态处理、填写处理结果

#### 核心交互

- 状态流转校验：仅允许「待处理 → 处理中 → 已完成」严格线性流转，非法操作禁用
- 超时报修单高亮标识：读取后端返回的 isOverdue 字段渲染，前端不自行计算超时
- 处理弹窗回填处理人、处理时间，提交后自动更新列表
- 提交报修前校验当前登录用户存在有效入住记录，无入住记录时前端提示禁止提交，后端接口兜底拦截

## 六、安全与交互规范

### 6.1 输入校验机制

- 所有表单必须开启前端校验，包含非空、长度、格式、范围校验
- 校验规则与后端保持一致，提交前拦截非法参数
- 特殊字符过滤，防范XSS风险，用户输入内容渲染时做转义处理
- 查询参数做长度与特殊字符限制，避免非法参数发往后端

### 6.2 权限控制粒度

1. **页面级**：路由守卫拦截，无权限角色无法访问对应页面
2. **菜单级**：侧边栏动态渲染，无权限菜单不展示
3. **按钮级**：核心操作按钮根据角色判断是否展示/禁用，如删除、办理入住
4. **数据级**：学生角色仅展示本人数据，查询接口由后端兜底，前端做展示适配

### 6.3 异常兜底机制

- 所有列表页必须实现：加载中骨架屏、空数据占位、请求错误重试入口
- 所有提交操作必须添加加载状态，禁止重复提交
- 接口失败时保留用户已填写内容，不得清空表单
- 全局404、403、500兜底页面，异常路由统一跳转

### 6.4 敏感信息处理

- 密码输入框使用密码类型，禁止明文展示
- 禁止在控制台日志、本地存储中明文存储密码等敏感信息
- 用户身份证、手机号等敏感信息展示时做脱敏处理

## 八、非功能设计保障

### 8.1 性能保障

- 路由懒加载，按需拆分页面代码，减小首屏包体积
- Element Plus按需引入，避免全量打包
- 列表数据分页加载，禁止一次性加载全量数据
- 合理使用Vue响应式，避免不必要的重渲染

### 8.2 可维护性保障

- 分层清晰，职责单一，模块间低耦合
- 统一请求、统一异常、统一组件，问题排查路径明确
- 核心方法、复杂逻辑、公共组件必须添加功能注释与使用说明
- 文件命名、变量命名遵循统一规范，见名知意

### 8.3 可扩展性保障

- 业务模块独立拆分，新增模块不影响现有代码结构
- 公共组件可复用，新增页面可快速基于通用组件搭建
- 状态、枚举模块化设计，新增业务状态无需改动核心逻辑

## 九、开发协作边界说明

1. **公共底座优先开发**：Day1完成请求封装、路由框架、状态管理、通用组件、环境配置等基础底座，作为所有业务开发的统一基础
2. **业务模块并行开发**：按业务模块分配开发人员，每人负责对应模块的页面、组件、接口封装，模块间通过公共能力交互，减少代码冲突
3. **接口契约先行**：开发前与后端对齐接口字段、请求参数、响应结构，基于接口文档并行开发，联调前完成本地Mock验证
4. **提交粒度**：按页面/功能点提交代码，单次提交对应单一功能，便于代码评审与问题回溯
5. **组件复用优先**：开发前先检查公共组件是否满足需求，优先复用，禁止重复开发同类组件
