**轻量化主干集成工作流**（基于 GitHub Flow 改良），核心原则为「主干唯一、分支短小、高频集成、轻量评审」。既完整覆盖 Git 协作的核心训练目标（分支隔离、PR 代码评审、冲突解决、版本可追溯），又砍掉所有非必要环节，匹配短周期快节奏的开发节奏，也更贴近中小团队真实开发模式。

## 一、分支模型

### 1. 长期分支（2个，全程保留）

| 分支名 | 定位         | 合并规则                                                     |
| ------ | ------------ | ------------------------------------------------------------ |
| `main` | 最终交付分支 | 存放稳定可运行的完整交付版本，整个项目周期仅合并 1-2 次（中期里程碑、最终验收），禁止直接提交 |
| `dev`  | 开发集成主干 | 日常开发的唯一基准分支，所有功能完成后均合并至此，必须保持随时可启动运行 |

### 2. 临时分支（从 `dev` 切出，合并后立即删除）

| 分支类型    | 命名规范                                                     | 使用场景           |
| ----------- | ------------------------------------------------------------ | ------------------ |
| `feature/*` | `feature/模块名-功能点`，例：`feature/repair-submit`、`feature/building-manage` | 新增功能、模块开发 |
| `bugfix/*`  | `bugfix/问题简述`，例：`bugfix/page-param-error`             | 缺陷修复、问题修正 |

### 3. 明确砍掉的冗余分支

- 移除 `release/*` 分支：本项目无多版本并行、无灰度发布需求，不需要版本发布分支
- 移除 `hotfix/*` 分支：无线上生产环境，所有缺陷修复统一走 `bugfix` 分支即可
- 移除所有辅助类分支：无多版本维护需求，不设 support、feature 等多层级分支

## 二、优化后全流程

将原串行的「测试→评审」改为并行，砍掉正式需求评审环节，对齐动作下沉到每日站会，全流程从 6 步压缩为 5 步，兼顾规范与效率。

```
需求对齐 → 分支开发 → 提PR（测试+评审并行） → 合并入dev → 最终交付合入main
   ↑                            ↓
   └────────── 缺陷修复 ↀ───────┘
```

### 阶段1：需求对齐与分配

- **载体**：核心需求统一录入 GitHub Issues 打标签（feat/bug/docs），小优化、小调整可口头对齐后补录，不搞形式化评审
- **对齐方式**：每日 10 分钟站会集中同步需求、分配责任人、确认验收标准，高优先级问题即时同步
- **输出**：明确到人、明确交付时间点，开发人员自行从 `dev` 切出对应分支开工

### 阶段2：分支开发与本地提交

1. 开发前先拉取 `dev` 最新代码，基于最新版本切出功能分支，禁止直接在 `dev`/`main` 上开发
2. 提交信息保留 Conventional Commits 规范（`feat/fix/docs/style/refactor`），这是协作练手核心点，不简化
3. **强制动作**：每日至少 1 次将 `dev` 最新代码合并到本地分支，提前解决小冲突，避免最终合并出现大规模冲突
4. 开发完成后对照验收标准完成本地自测，未自测代码禁止提 PR

### 阶段3：PR 提交 + 测试 + 代码评审（并行执行）

原流程「先测试、后评审」串行改为并行，提 PR 后功能验证与代码审查同时进行，大幅节省时间。

1. **PR 提交**：目标分支统一为 `dev`，禁止直提 `main`；PR 内容精简为 3 项：关联 Issue、变更概述、自测结论
2. 并行处理
   - 测试人员拉取分支验证功能，对照验收标准检查核心流程，发现问题直接在 PR 内评论
   - 评审人员同步开展代码审查，聚焦规范、架构、安全性、健壮性四个维度
3. 评审规则简化
   - 普通业务功能：1 人评审通过即可
   - 公共基础模块（权限拦截、统一返回、数据库配置、事务逻辑）：2 人评审通过
4. **缺陷修复**：PR 评审期间发现问题，开发人员在当前功能分支直接修复推送，PR 自动更新，重新验证即可；功能已合并入 `dev` 后发现问题，必须新建 `bugfix/*` 分支修复并重新走 PR 流程（功能分支合并后已删除，禁止在已删除分支上继续操作）

### 阶段4：合并入 dev + 每日集成

1. **合并条件**：测试通过 + 评审通过，双条件满足即可合并
2. **合并方式**：统一使用 **Squash Merge**，将分支多次提交压缩为 1 条干净记录并入 `dev`，保持主干历史整洁
3. **合并后动作**：立即删除对应功能分支，避免仓库分支堆积
4. **关键规则**：**每日下班前完成当日完工功能的合并**，做到日粒度集成，所有人第二天基于最新 `dev` 开工，从根源降低跨分支冲突概率

### 阶段5：最终交付合入 main

1. 全量功能开发完成、整体回归测试通过后，一次性将 `dev` 合并入 `main`，作为最终交付版本
2. 合并前做一次全流程走查，确保 `main` 分支始终是稳定、可部署、可验收的完整版本
3. 合并后打上版本标签（如 `v1.0`），作为交付里程碑

## 三、核心取舍说明

### 1. 砍掉的冗余环节（不适合本项目）

1. **砍掉多层长期分支**：无多版本运维、无线上修复需求，release/hotfix 分支完全无用
2. **砍掉串行审批流程**：小团队并行处理效率更高，不用等测试完成再启动代码评审
3. **砍掉强制 Issue 编号绑定**：项目规模小、功能边界清晰，不用强制分支名、提交信息绑定 Issue 编号，降低流程门槛
4. **砍掉多层审批机制**：生产级项目需要多级审批，本项目普通功能 1 人评审足够

### 2. 必须保留的核心能力（练手目标，不能省）

1. **保留分支隔离开发**：禁止直接提交主干，所有人必须走「功能分支 → PR → 合并」流程，这是团队协作的基础
2. **保留 PR 代码评审**：强制交叉评审，既保障代码质量，也是练手核心目标（熟悉团队代码评审流程）
3. **保留规范化提交**：统一 Commit 格式，培养可追溯的提交习惯
4. **保留主干可运行原则**：`dev` 分支随时可启动运行，禁止合入无法运行的半截代码

## 四、补充落地实用规则

### 1. 快速通道规则

以下场景可简化流程，提升效率：

- 纯文档修改、配置调整、注释补充：1 人秒审即可合并，无需完整测试
- 极小缺陷修复（文案修正、样式调整、参数补全）：单人评审通过即可，不用全流程验证
- **红线**：核心业务逻辑、公共基础模块严禁走快速通道

### 2. 冲突处理规则

- 优先预防：每日拉取 `dev` 最新代码，开发时尽量不改动他人负责的模块文件
- 冲突归属：谁的分支产生冲突，谁负责解决；公共文件冲突召集相关人对齐后再合并，禁止私自覆盖他人代码
- 解决后必须重新自测，确认功能正常再继续评审

### 3. 提交与文件规范

- 提倡小步提交，单次提交对应单一逻辑变更，禁止「几百行代码一次性提交、同时修改多个功能」
- 本地配置文件、依赖包、编译产物、IDE 配置必须通过 `.gitignore` 过滤，禁止提交到仓库
- 禁止提交调试用的临时硬编码、注释掉的废代码

### 4. 回退规则

- 合并后发现严重问题，优先使用 `git revert` 回退对应提交，不要直接硬改代码
- 回退操作必须同步通知全员，避免其他人基于错误代码继续开发

### 5. GitHub 分支保护配置（平台强制红线）

将「禁止直推主干」由文档约束升级为平台强制，GitHub 仓库创建后立即配置：

- 进入仓库 → `Settings` → `Branches` → `Add branch protection rule`
- 对 `main`、`dev` 分别添加规则：
  1. `Require a pull request before merging`：开启
  2. `Require approvals`：1 人（与评审规则一致）
  3. `Block force pushes`：开启
- 生效后：直接向 `main` / `dev` 推送会被平台拒绝，必须走 PR；评审通过数不达标无法合并

## 五、合并验收红线

出现以下任意情况，禁止合并代码：

1. 直接向 `main` / `dev` 分支推送代码，未走 PR 流程
2. 功能未自测、存在阻断性运行错误
3. 核心公共模块评审不通过，存在架构、安全、规范问题
4. 存在严重编码违规：静默吞异常、SQL 注入风险、大量魔法值硬编码
5. 引入未约定的第三方依赖，影响项目环境一致性
